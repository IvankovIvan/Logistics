Project №1.5.a — Warehouses Geometry Invariants

⸻

1. Назначение шага

Project №1.5.a закрывает геометрическую семантику складов на карте в рамках Project №1.

Цель шага — обеспечить корректное, устойчивое и однозначное визуальное представление абсолютного текущего количества товара на складе, без добавления интерактивности, аналитики или бизнес-логики на фронте.

Этот шаг намеренно ограничен только геометрией точек складов и является фундаментом для:
	•	подписей (Project №1.5.b),
	•	общего итога (Project №1.6),
	•	дальнейшего расширения визуала без рефакторинга базовой геометрии.

⸻

2. Инварианты визуализации складов

Жёстко зафиксированы следующие инварианты:
	•	Каждый склад всегда видим на карте.
	•	Геометрия складов не содержит бизнес-логики.
	•	Визуализация использует абсолютное значение quantity, полученное из API.
	•	Отсутствие quantity у склада считается ошибкой контракта, а не допустимым состоянием.
	•	Frontend ничего не считает и не агрегирует, кроме чисто визуальной функции радиуса.
	•	Радиус кодирует только quantity и не зависит от других параметров.

⸻

3. Источник данных

Единственный источник данных для геометрии складов:
GET /api/map
  → MapWarehouse.quantity

Свойства:
	•	quantity — абсолютное текущее значение.
	•	Значение уже является current-state.
	•	Frontend не интерпретирует происхождение quantity.
	•	Любые дельты, суммы, перерасчёты запрещены.
	•	Если API возвращает склад без quantity, это считается ошибкой backend-контракта.

⸻

4. Геометрическая модель склада
	•	Тип слоя: MapLibre circle-layer
	•	Геометрия: Point (lon, lat)
	•	Соответствие:
	•	1 склад = 1 feature
	•	Координаты склада:
	•	фиксированы,
	•	не изменяются масштабом,
	•	не зависят от состояния или quantity.

Порядок слоёв:
	•	Слой складов располагается под маршрутами.
	•	Геометрия складов не перекрывает семантику движения (Project №1.3).

⸻

5. Масштабирование радиуса точки

Размер точки склада кодирует только количество товара.

Формула (инвариант)

radius = clamp(
  minR + k * log10(quantity + 1),
  minR,
  maxR
)

Обязательные элементы формулы
	•	quantity + 1 — чтобы quantity = 0 отображался корректно.
	•	log10 — обязателен для логарифмического масштабирования.
	•	minR — гарантирует видимость нулевых и малых значений.
	•	maxR — защищает карту от “заливания” при экстремальных данных.
	•	k — коэффициент визуальной чувствительности.

Архитектурная фиксация
	•	Вычисление радиуса выполняется в circle-layer expression, а не в transform.
	•	transform.ts только прокидывает quantity как свойство feature.
	•	Никакие числовые преобразования не выполняются вне слоя визуализации.

Важно:
	•	Это чисто визуальная функция.
	•	Она не отражает экономическую, логистическую или аналитическую модель.
	•	Масштабирование не зависит от zoom (фиксированная геометрия данных).

⸻

6. Константы визуализации

Константы minR, maxR, k:
	•	Являются частью фронтенд-конфигурации.
	•	Не захардкожены в transform.
	•	Не вычисляются динамически.
	•	Подбираются эмпирически.
	•	Их изменение не должно требовать рефакторинга слоя.

⸻

7. Визуальные ограничения

В рамках Project №1.5.a строго запрещено:
	•	❌ кодировать quantity цветом;
	•	❌ кодировать quantity прозрачностью;
	•	❌ кодировать quantity обводкой;
	•	❌ добавлять hover, focus или интерактивные состояния;
	•	❌ добавлять подписи или tooltip’ы;
	•	❌ изменять API или backend.

Единственный визуальный канал кодирования quantity — радиус круга.

⸻

8. Symbol-layer (задел)
	•	Использование symbol-layer допускается архитектурно.
	•	В рамках 1.5.a:
	•	слой может существовать,
	•	но обязан быть выключен.
	•	Symbol-layer зарезервирован исключительно для:
	•	Project №1.5.b (подписи складов),
	•	без изменения геометрии circle-layer.

⸻

9. Критерии готовности (Definition of Done)

Шаг считается завершённым, если:
	•	Любое quantity ≥ 0 отображается на карте.
	•	quantity = 0 визуально различимо и не пропадает.
	•	Большие значения не доминируют над остальными.
	•	Масштабирование радиуса стабильно при любых данных.
	•	Масштаб не зависит от количества складов.
	•	Ни один другой слой не зависит от quantity.
	•	Геометрия складов не требует изменений для следующих этапов.

⸻

10. Осознанные ограничения

Project №1.5.a не включает:
	•	подписи складов;
	•	числовые значения на карте;
	•	tooltip’ы;
	•	интерактивность;
	•	аналитику;
	•	изменения API или backend;
	•	изменения семантики Project №1.3.

Это не упущения, а зафиксированные границы шага.

⸻

11. Связь со следующими этапами
	•	Project №1.5.b — подписи складов и числовые значения (symbol-layer).
	•	Project №1.6 — общий итог (бейдж).
	•	Гарантия: геометрия складов из 1.5.a не подлежит рефакторингу в следующих этапах.
	•	Радиус circle-layer остаётся неизменным в последующих шагах.
