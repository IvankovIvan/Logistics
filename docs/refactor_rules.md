Refactoring Rules (Universal)

Этот файл — постоянная памятка для рефакторинга. Его цель — не придумывать правила заново, а поднимать и применять их перед каждым рефакторингом.

⸻

0. Базовый принцип

Рефакторинг ≠ изменение поведения.
Если поведение меняется — это отдельная задача/шаг/PR с явно обозначенной целью.

⸻

1. Порядок работы (обязательный)
	1.	Сначала смотрим код и факты, а не предполагаем.
	2.	Фиксируем инварианты (что обязано остаться неизменным).
	3.	Определяем границы ответственности.
	4.	Только потом переносим, чистим и переименовываем.

⸻

2. Инварианты (то, что нельзя ломать)
	•	Один источник правды для данных.
	•	Идемпотентность: порядок входящих данных не влияет на результат.
	•	Ошибки не обнуляют данные, если используется soft-fail.
	•	Таймеры, подписки и слушатели корректно чистятся.
	•	Нет скрытых повторных запросов или эффектов.

⸻

3. Разделение по ответственности (слои)
	•	Оркестратор (page / container) — композиция экрана, состояние UI.
	•	Данные — fetch, polling, cache, soft errors.
	•	Трансформации — чистые функции (model → view-model).
	•	Интеграции — карты, графики, SDK, внешние библиотеки.

Правило: если модуль можно описать глаголом — он должен быть отдельным.

⸻

4. Размер файла — не критерий

Критерий — роль файла:
	•	Оркестратор не знает деталей SDK.
	•	Слой данных не знает про UI.
	•	Интеграция не знает про fetch и бизнес-логику.

⸻

5. Конфигурация и env
	•	process.env читается только в одном месте (например lib/config.ts).
	•	В клиентском коде используются только NEXT_PUBLIC_*.
	•	Парсинг, дефолты и валидация — там же.
	•	Настройка через .env — это техническая настройка, не UI-фича.

⸻

6. React-эффекты
	•	useEffect не должен зацикливаться от собственного результата.
	•	Один setInterval / подписка → один cleanup.
	•	Сетевые запросы должны иметь abort/race-защиту: старый ответ не перетирает новый.

⸻

7. Мягкие ошибки (soft-fail)
	•	При ошибке обновления данные сохраняются.
	•	Меняется только статус ошибки.
	•	lastUpdated обновляется только при success.
	•	Экран остаётся читаемым и стабильным.

⸻

8. Интеграции (карты, SDK, визуализации)
	•	Инициализация SDK — один раз.
	•	Sources / Layers / Listeners — один раз.
	•	Обновление данных — через setData или аналоги, без пересоздания SDK.
	•	Визуальные решения (цвета, стили, темы) живут только в слое рендера.

⸻

9. Комментарии (чтобы меньше переспрашивать)
	•	В начале каждого файла: что делает модуль и какие инварианты защищает.
	•	У опасных мест (таймеры, abort, setData, soft errors) — комментарий “почему так”.

⸻

10. Шаги и PR
	•	Один шаг = один смысл.
	•	Сначала перенос без изменения поведения.
	•	Изменение поведения — отдельный шаг.
	•	После каждого шага: сборка + быстрый smoke-check.

⸻

11. Anti-patterns (что запрещено при рефакторинге)

Этот раздел — список типовых ошибок, из-за которых рефакторинг превращается в деградацию проекта.

11.1 Смешивание слоёв

❌ Fetch / polling / бизнес-логика внутри UI-компонентов.
❌ SDK (карты, графики) напрямую дергают API.
❌ Оркестратор знает детали рендера.

Причина: код становится нерасширяемым и ломается при первой новой фиче.

⸻

11.2 «Незаметное» изменение поведения

❌ Рефакторинг, который «случайно» меняет тайминги, частоту запросов или порядок обновлений.
❌ Обновление lastUpdated при ошибке.
❌ Очистка данных при временной ошибке сети.

Причина: невозможно понять, где баг — в логике или в рефакторинге.

⸻

11.3 Раздувание оркестратора

❌ page.tsx/container знает про MapLibre, SQL, SDK, формулы, цвета, алгоритмы.
❌ Оркестратор выполняет преобразования данных.

Причина: файл становится «точкой боли», где невозможно безопасно менять код.

⸻

11.4 Мелкое дробление без смысла

❌ Файлы по 20–30 строк без чёткой ответственности.
❌ Вынос «ради выноса», а не ради роли.

Причина: код становится труднее читать, чем до рефакторинга.

⸻

11.5 Преждевременный оверинжиниринг

❌ Context / Redux / Zustand без реальной необходимости.
❌ Абстракции «на будущее», которое не наступило.
❌ Универсальные фабрики ради одной реализации.

Причина: усложнение без выгоды и рост когнитивной нагрузки.

⸻

11.6 Отсутствие комментариев в опасных местах

❌ Таймеры, abort, setData, soft-fail без объяснения.
❌ Магические числа и условия без комментариев.

Причина: через месяц никто не понимает, почему код нельзя «упростить».

⸻

11.7 Чтение env где попало

❌ process.env в нескольких файлах.
❌ Парсинг env без дефолтов и валидации.

Причина: нестабильное поведение между окружениями.

⸻

11.8 Рефакторинг без фиксации результата

❌ Нет smoke-check после шага.
❌ Нет понимания «что именно улучшилось».

Причина: рефакторинг превращается в бесконечный процесс без точки опоры.

⸻

12. Anti-patterns by layer (по слоям)

12.1 Оркестратор (page / container)

❌ Знание деталей SDK (MapLibre, Chart.js и т.п.).
❌ Преобразование данных (GeoJSON, форматирование моделей).
❌ Чтение process.env.
❌ Управление таймерами/abort напрямую, если есть выделенный data-слой.

Правило: оркестратор склеивает, но не вычисляет и не интегрирует.

⸻

12.2 Слой данных (fetch / polling)

❌ Знание про UI (цвета, подписи, layout).
❌ Манипуляции DOM или SDK.
❌ Несколько источников правды.
❌ Сброс данных при временной ошибке.

Правило: слой данных знает только факты и их актуальность.

⸻

12.3 Трансформации (model → view-model)

❌ Побочные эффекты.
❌ Зависимость от React, env, таймеров.
❌ Использование глобального состояния.

Правило: функции должны быть чистыми и детерминированными.

⸻

12.4 Интеграции / SDK (карта, графики)

❌ Fetch данных напрямую.
❌ Хранение бизнес-состояния.
❌ Повторная инициализация SDK при каждом обновлении.

Правило: интеграция рисует и слушает, но не решает, что рисовать.

⸻

12.5 Конфигурация

❌ Чтение env в каждом модуле.
❌ Магические дефолты без комментариев.
❌ Смешивание продуктовых и технических настроек.

Правило: конфиг — единая точка, с объяснёнными инвариантами.

⸻

13. Чеклист «5 минут перед рефакторингом»

Используй этот чеклист каждый раз перед началом рефакторинга.
Если на какой‑то пункт нет чёткого ответа — рефакторинг рано начинать.

1. Поведение
	•	Я могу одним предложением описать текущее поведение кода.
	•	Я понимаю, что именно нельзя менять.
	•	Если поведение всё‑таки меняется — это отдельная задача.

⸻

2. Инварианты
	•	Источник правды для данных один.
	•	Ошибки не обнуляют данные (если это soft‑fail сценарий).
	•	Таймеры / подписки / listeners имеют cleanup.
	•	Порядок данных не влияет на результат.

⸻

3. Границы ответственности
	•	Я могу показать, где оркестратор.
	•	Я могу показать, где слой данных.
	•	Я могу показать, где трансформации.
	•	Я могу показать, где интеграции / SDK.

⸻

4. Anti‑patterns
	•	Я не смешиваю слои.
	•	Я не делаю «вынос ради выноса».
	•	Я не добавляю абстракции без реальной необходимости.
	•	Я не читаю env вне конфига.

⸻

5. Комментарии и фиксация смысла
	•	В каждом новом/изменённом файле есть комментарий «что делает модуль».
	•	В опасных местах есть комментарий «почему так».
	•	Я понимаю, что именно улучшилось после рефакторинга.

⸻

6. После шага
	•	Проект собирается.
	•	Экран/функция работает как раньше.
	•	Есть быстрый smoke‑check.

⸻

Использование
	1.	Прочитать разделы 0–3.
	2.	Просмотреть разделы 11–12 (Anti‑patterns).
	3.	Пройти чеклист из раздела 13.
	4.	Только после этого начинать рефакторинг.

⸻

14. Шаблон PR: Refactor Justification

Используй этот шаблон для каждого PR с рефакторингом.
Цель — зафиксировать, почему изменения безопасны и что именно улучшилось.

1. Цель рефакторинга

Зачем:
	•	Коротко: что было не так и почему понадобился рефакторинг.
	•	Без слов «на будущее» и «потом пригодится».

⸻

2. Гарантии неизменности поведения

Что НЕ изменилось:
	•	Внешнее поведение (UI / API / контракты)
	•	Частота запросов / тайминги
	•	Обработка ошибок

Если что-то изменилось — указать явно и сослаться на отдельную задачу.

⸻

3. Инварианты

Какие инварианты соблюдены:
	•	Один источник правды для данных
	•	Идемпотентность
	•	Корректный cleanup эффектов
	•	Soft-fail (если применимо)

⸻

4. Что улучшилось

Конкретно:
	•	Читаемость (что стало проще понять)
	•	Границы ответственности (что теперь изолировано)
	•	Возможность дальнейших изменений (без переписывания)

⸻

5. Anti-patterns check

Подтверждение:
	•	Слои не смешаны
	•	Нет выноса ради выноса
	•	Нет новых абстракций без необходимости
	•	Конфиг не размазан

⸻

6. Проверки

Что проверено:
	•	Проект собирается
	•	Smoke-check выполнен
	•	Ключевые сценарии работают

⸻

7. Область изменений

Затронутые модули:
	•	Список файлов / директорий

⸻

8. Ограничения

Что сознательно НЕ делалось в этом PR:
	•	(например: не добавлялся polling, не менялся UI, не трогались стили)

⸻

Если этот шаблон заполнен честно — PR можно ревьюить по сути, а не по догадкам.
