Project №1.4.b — Расширение контракта /api/map полем quantity

Цель

Зафиксировать минимальное и совместимое расширение контракта /api/map, необходимое для визуальных инвариантов складов (Project №1.5), без изменения смысла API и без превращения витрины в аналитику.

⸻

Текущее состояние (факт)

MapWarehouse в контракте /api/map не содержит информации о количестве товара на складе.
Следствие: фронт не может реализовать визуальные инварианты складов.

⸻

Принцип расширения

Расширение контракта должно быть:
	•	аддитивным (backward compatible по структуре ответа),
	•	однозначным (одно поле — один смысл),
	•	current-state (без истории и расчётов).

⸻

Новый контракт (концептуально)

MapWarehouse

Добавляется обязательное поле:
quantity: number


⸻

Семантика поля quantity
	•	абсолютное текущее количество товара на складе;
	•	относится к моменту “сейчас”;
	•	может быть 0;
	•	не агрегированное и не производное;
	•	передаётся напрямую из warehouse current-state;
	•	подчиняется event_time и правилам stale/out-of-order наравне с остальными полями склада.

⸻

Обязательность и ошибки контракта
	•	Поле quantity обязательно для каждого MapWarehouse.
	•	Отсутствие quantity — ошибка контракта.
	•	Склад без quantity не должен присутствовать в ответе /api/map.
	•	Никакой нормализации, подстановки 0 или fallback на read-side не допускается.

⸻

Совместимость с существующими этапами

Project №1.1–1.2
	•	ingest остаётся идемпотентным;
	•	stale-защита не меняется.

Project №1.3
	•	маршруты и их визуализация не затрагиваются.

Frontend
	•	получает достаточные данные для Project №1.5;
	•	не выполняет вычислений и агрегаций.

⸻

Что сознательно НЕ делаем в этом документе
	•	не описываем формат ingest-события;
	•	не меняем БД;
	•	не обсуждаем поставки/продажи;
	•	не добавляем аналитику.

⸻

Итог

После принятия данного контракта:
	•	/api/map содержит обязательное поле quantity;
	•	контракт становится достаточным для визуальных инвариантов складов;
	•	Project №1.5 может быть реализован без архитектурных рисков.
