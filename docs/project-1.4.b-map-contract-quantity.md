Project №1.4.b — Расширение контракта /api/map полем quantity

Цель
Зафиксировать минимальное и совместимое расширение контракта /api/map, необходимое для визуальных инвариантов складов (Project №1.5), без изменения смысла API и без превращения его в аналитический.

⸻

Текущее состояние (факт)

MapWarehouse в контракте /api/map не содержит информации о количестве.

Следствие:
	•	фронт не может:
	•	масштабировать точки складов,
	•	отображать числовые остатки,
	•	выполнять инварианты Project №1.5.

⸻

Принцип расширения

Расширение контракта должно быть:
	•	аддитивным (backward compatible),
	•	однозначным (одно поле — один смысл),
	•	current-state (без истории и расчётов).

⸻

Новый контракт (концептуально)

MapWarehouse

Добавляется поле:
quantity: number

Семантика:
	•	абсолютное текущее количество товара на складе;
	•	всегда относится к моменту “сейчас”;
	•	может быть 0;
	•	не агрегированное и не производное.

⸻

Инварианты поля quantity
	•	❌ не сумма входов/выходов;
	•	❌ не “ожидаемое” количество;
	•	❌ не вычисляется read-side;
	•	✅ передаётся напрямую из warehouse current-state;
	•	✅ подчиняется event_time как и другие поля склада.

⸻

Поведение при отсутствии данных

Если quantity неизвестно или не задано:
	•	значение обязано быть 0, а не null;
	•	фронт не должен гадать или скрывать склад.

Это упрощает визуальную логику и убирает ветвления.

⸻

Совместимость с существующими этапами

Project №1.1–1.2
	•	ingest остаётся идемпотентным;
	•	stale-защита не меняется;
	•	никаких новых типов событий пока не вводится (это следующий шаг).

Project №1.3
	•	маршруты не затрагиваются;
	•	фильтрация и визуальные инварианты маршрутов не меняются.

Frontend
	•	может реализовать:
	•	размер точки ∝ quantity,
	•	числовые подписи,
	•	минимальный размер при quantity = 0.

⸻

Что сознательно НЕ делаем в этом шаге
	•	не описываем формат ingest-события;
	•	не меняем БД;
	•	не обсуждаем поставки/продажи;
	•	не добавляем аналитику.

Это чистая фиксация контракта.

⸻

Итог

После принятия 1.4.b:
	•	/api/map официально содержит quantity,
	•	фронт получает все данные для Project №1.5,
	•	можно переходить к реализации без архитектурных рисков.
