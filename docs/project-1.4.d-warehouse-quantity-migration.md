Project №1.4.d — Миграция quantity в current-state (DB + ingest контракт)

Цель

Зафиксировать архитектурную модель появления quantity в системе Project №1 без реализации кода и без нарушения инвариантов Project №1.1–1.3.

⸻

Принятый контекст
	•	quantity — абсолютное значение;
	•	источник истины — событие склада;
	•	read-side и фронт ничего не считают;
	•	/api/map — витрина current-state.

⸻

Финальное состояние (целевое)

1️⃣ Current-state БД

В таблице warehouses_current присутствует поле:
quantity BIGINT NOT NULL

Семантика:
	•	хранит текущее абсолютное количество;
	•	обновляется вместе с остальными полями склада;
	•	подчиняется last_event_time.

⸻

2️⃣ Ingest payload (warehouse)

Событие entity_type = "warehouse" обязано содержать:
quantity: number

Правила:
	•	отсутствие quantity → логическая ошибка (rejected);
	•	stale-событие → quantity не меняется;
	•	duplicate → игнорируется;
	•	applied → quantity перезаписывается.

⸻

3️⃣ Read-side (/api/map)

MapWarehouse содержит обязательное поле:
quantity: number

Правила:
	•	read-side не вычисляет и не агрегирует;
	•	склад без quantity не попадает в /api/map;
	•	нормализация и fallback запрещены.

⸻

Миграционный факт (описательно)

До внедрения quantity:
	•	склады могут существовать в current-state без quantity;
	•	такие склады считаются невалидными для /api/map;
	•	Project №1.5 остаётся заблокирован.

Миграция считается завершённой, когда:
	•	все warehouse-события содержат quantity;
	•	current-state складов полностью заполнен;
	•	/api/map не содержит складов без quantity.

⸻

Совместимость
	•	ingest уже поддерживает idempotency и stale-защиту;
	•	добавляется одно обязательное поле без изменения потоков;
	•	маршруты и визуал Project №1.3 не затрагиваются.

⸻

Жёсткие границы
	•	не добавляем supply/sale;
	•	не трогаем shipments;
	•	не считаем “в пути”;
	•	не делаем UI;
	•	не вводим аналитику.

⸻

Итог

quantity архитектурно легализован как first-class current-state поле.
/api/map становится честным источником абсолютных значений.
Project №1.5 разблокирован.
