# Architecture

Архитектура проекта **Logistics** спроектирована так, чтобы:
- фронтенд был максимально тупым,
- формат API был стабильным,
- источники данных можно было менять без переписывания UI,
- логика была разделена по слоям.

---

## Общая схема

```
Browser
  │
  ▼
Nginx (reverse proxy)
  │
  ├── /            → Next.js (frontend)
  └── /api/*       → FastAPI (backend)
                        │
                        ▼
                  routers (HTTP слой)
                        │
                        ▼
                  services (бизнес-логика)
                        │
                        ▼
                  domain (контракты, нормализация)
                        │
                        ▼
               FAKE_* / БД / ingest (в будущем)
```

---

## Слои и ответственность

### 1. Nginx

**Роль:** единая точка входа.

- `/` → frontend (Next.js)
- `/api/*` → backend (FastAPI)
- backend **не доступен напрямую снаружи**

Nginx не знает ничего о бизнес-логике.

---

### 2. Frontend (`web/`)

**Роль:** отображение данных.

- делает **один запрос**: `/api/map`
- не склеивает данные
- не знает, откуда они пришли
- работает только с контрактом API

Если структура ответа стабильна — фронт не меняется.

---

### 3. Routers (`app/routers/`)

**Роль:** HTTP-слой.

- FastAPI endpoints
- валидация входных параметров
- описание OpenAPI
- **никакой бизнес-логики**

Пример:
```text
routers/map.py
```

Router:
- принимает запрос
- передаёт данные в `services`
- возвращает результат

---

### 4. Services (`app/services/`)

**Роль:** бизнес-логика.

- сборка данных
- агрегации
- правила отображения
- единая точка, где меняется логика

Пример:
```text
services/map_builder.py
```

Именно здесь:
- FAKE_* можно заменить на БД
- ingest можно подключить без изменения router'ов

---

### 5. Domain (`app/domain/`)

**Роль:** контракты и нормализация данных.

Содержит:
- `Protocol`-интерфейсы (`WarehouseLike`, `ShipmentLike`)
- приведение enum (`coerce_enum`)
- нормализацию источников (`dict → object`)

Domain **не знает**:
- откуда данные
- как они отображаются
- про HTTP

Это «чистая логика».

---

### 6. Models (`app/models/`)

**Роль:** контракты API.

- Pydantic-модели
- enums (`WarehouseStatus`, `ShipmentStatus`)
- структуры ответа (`MapResponse`, `MapWarehouse`, `MapRoute`)

Модели:
- используются и в backend, и во frontend
- фиксируют формат данных

---

## Ключевой endpoint: `/api/map`

### Почему один endpoint

- фронт делает **1 запрос**
- нет гонок между `/warehouses` и `/shipments`
- проще кэшировать
- проще менять backend

### Формат

```json
{
  "warehouses": [...],
  "routes": [...]
}
```

Этот контракт считается **стабильным**.

---

## Почему так, а не иначе

❌ Не:
- router с логикой
- фронт, который собирает данные
- жёсткая привязка к БД

✅ Да:
- чистые слои
- расширяемость
- понятные точки изменения

---

## Будущее развитие

- ingest-сервис (запись в БД)
- витрина «на сейчас»
- история маршрутов
- авторизация
- кэширование

Архитектура уже готова к этому без переписывания проекта.

---

## TL;DR

- **router** — HTTP
- **service** — логика
- **domain** — контракты
- **models** — формат данных
- **frontend** — просто рисует

Если слой начинает «знать лишнее» — это архитектурная ошибка.
