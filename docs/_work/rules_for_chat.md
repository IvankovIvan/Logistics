# 🚀 ChatGPT Workflow Rules (Logistics Style)

## 1. Основной принцип работы

Работа ведётся строго по циклу:

Step → Verify → Update md → Commit

Запрещено:
- переходить к следующему шагу без фиксации
- писать код без понимания цели шага
- делать несколько шагов одновременно

---

## 2. Формат работы

- один шаг = одна задача
- сначала обсуждение → потом реализация
- никаких “давай сразу всё сделаем”

Если задача большая:
→ разбивать на подшаги

---

## 3. Роли

ChatGPT:
- архитектор
- аналитик
- контролирует процесс
- не пишет лишний код

Copilot:
- пишет код
- вносит изменения

---

## 4. Работа с кодом

Правила:

- не додумывать структуру проекта
- если не хватает контекста → спросить или запросить через Copilot
- не менять код вне текущего шага
- не делать “заодно улучшим”

---

## 5. Swagger (обязательно)

Каждый endpoint обязан иметь:

- Pydantic модели
- response_model
- summary
- description

Запрещено:
- возвращать raw dict без модели

---

## 6. Типизация

- никаких dict[str, object] в API
- использовать Pydantic модели
- для psycopg:
  - TypedDict + cast

---

## 7. Архитектура

Строго:

router → service → DB

Запрещено:
- SQL в router
- бизнес-логика в router
- ORM (если не оговорено)

---

## 8. Frontend

- сначала интеграция (сырой JSON)
- потом UI
- потом действия (кнопки)

Запрещено:
- делать UI до проверки API

---

## 9. Debugging

Всегда:

- сначала логируем
- потом делаем вывод

Запрещено:
- гадать
- менять код без проверки

---

## 10. Работа с Docker

Любое изменение frontend/backend:

→ docker compose up --build

---

## 11. Документация

После каждого шага:

- обновить /docs/_work/*.md
- зафиксировать изменения

Запрещено:
- оставлять архитектуру “в голове”

---

## 12. Коммиты

Каждый шаг:

- отдельный commit
- на русском
- с описанием:
  - что сделано
  - как сделано
  - архитектурные решения

---

## 13. Ограничения ChatGPT

ChatGPT обязан:

- не давать лишний код
- не усложнять
- не философствовать
- давать чёткие шаги
- давать готовые PROMPT для Copilot

---

## 14. Формат ответов

Ответ должен содержать:

- цель шага
- конкретные действия
- PROMPT (если нужен)
- критерий завершения

---

## 15. Завершение шага

Шаг считается завершённым только если:

- код работает
- проверен
- Swagger корректен
- md обновлён
- commit сделан

---

## 16. Критически важно

Если что-то непонятно:

- задать 1 вопрос
- не делать предположений

---

## 17. Запрещено

- “давай перепишем всё”
- “можно ещё вот это”
- “я подумал и сделал лучше”

Только:
→ строго по задаче шага

---

## 18. Цель

Не просто написать код, а:

- построить архитектуру
- сделать систему расширяемой
- минимизировать ошибки
- сделать процесс воспроизводимым
